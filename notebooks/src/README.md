# How the notebooks are made

Every notebook is generated by a Python script in this folder, using `scripts/nb.py`.
Edit the script, not the `.ipynb`. Then generate and run:

```bash
python3 notebooks/src/f01_how_models_learn.py                       # writes the .ipynb (no outputs)
python3 scripts/run_notebook.py notebooks/fields/01_how_models_learn.ipynb   # runs it top to bottom, saves outputs, records runtime
```

`notebooks/src/f01_how_models_learn.py` is the reference. Match its structure and voice.

---

## Structure of a taste-project notebook

1. `nb.header(...)`: Colab badge, title (the field's question), **In short** box, and **"Where you'll end up"** with a picture of the final output. The picture must be real output (generate it in `make_end_image()` by actually running the code), never a mock-up.
2. "How to use this notebook" (short; copy from the reference).
3. Sections, each opening with a **problem**, then **see it → what it means → what it's called → formula → by hand → in code**.
   - Headings are plain statements or questions ("Which way should a number move? Nudge it and see"), not textbook labels.
   - `nb.predict(prompt, answer)` before reveals. The answer is one click away (a `<details>` block).
   - 🐍 **Python notes** after the first use of any new Python feature (classes, comprehensions, dicts, `heapq`, decorators, f-strings, slicing, numpy broadcasting...). The student knows programming, not Python. Keep each note to 2–4 bullets.
   - Build **from scratch first** (plain Python / numpy), **then the library version** (PyTorch, scikit-learn, Gymnasium, OR-Tools...), then check they agree.
4. **Practice**: `nb.exercise(n, text, starter, solution_src=... or solution_md=...)`. Problems must not name the method to use. Solutions go in collapsed cells (never deleted).
5. `nb.cue([...])`: "When you see ___ in a problem, think ___."
6. `nb.footer(experiments=[2–3 "try changing this"], questions=[the field's open research questions from BUILD_BRIEF Section 4], field_name=...)`: adds Try changing this, Open research questions, Spark Log prompts.
7. A short "Go deeper" with the resources from BUILD_BRIEF Section 4 (URLs are in `site/src/data/fields.ts`; they were verified).

## Wording (BUILD_BRIEF Section 2a)

- Short sentences (≤ 20 words). One idea per sentence. Plain words. Use "you".
- One **bold** key idea per block, at most.
- No term before it is explained. Name things *after* showing them.
- Banned: simply, just, obviously, clearly, trivially, "it's easy to see", "recall", "note that", "it turns out", hype, exclamation marks, analogies (fruit, shopping, cooking, factories, sports, machines that "eat"), personification ("the model wants / thinks / knows").
- Every number you state in markdown must match what the code prints. After running, read the outputs and fix the text.
- Colours in plots: green = data/input, red = weights/adjusted values, yellow/amber = results/output.

## Running rules

- Must run top to bottom on Google Colab's free CPU in under ~20 minutes (aim for under 10 here; this machine has 4 cores).
- Libraries: numpy, matplotlib, pandas, scikit-learn, PyTorch, Gymnasium. Anything else: one `!pip install -q ...` line in the first code cell. (Write it as `%pip install -q ...` so it also works outside Colab.)
- No internet needed except for datasets that may fail; always have a fallback (e.g. scikit-learn's bundled data).
- Interactive play (e.g. `input()`) must be behind a flag (`PLAY = False`) so the notebook runs unattended.
- Animations: `matplotlib.animation.FuncAnimation(...).to_jshtml()` displayed with `IPython.display.HTML`. Keep under ~40 frames and small figures (the notebook file should stay under ~5 MB).
- Seed every random generator so outputs are reproducible.

## Checks before committing

```bash
python3 scripts/run_notebook.py <notebook>        # must pass; runtime is recorded
node scripts/check-wording.mjs --nb-only          # must report 0 hits for your notebook
```
